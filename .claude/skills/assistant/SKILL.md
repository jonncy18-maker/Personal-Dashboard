## AI Assistant

**The AI Assistant is the app's sixth AI use — the one agentic surface, and the one non-Haiku model.** A floating chat panel on every page (`components/AssistantPanel.jsx`, mounted in `AppShell`) posts to `/api/assistant`, where `lib/assistant.js` runs a Claude Sonnet (`claude-sonnet-5`) tool loop. Rules that keep it honest and inside the app's boundaries:

- **Its tools are an explicit allowlisted catalog of this app's OWN api routes, called over same-origin fetch** — the assistant does exactly what the UI does, through the same validation, geocoding, photo caching, PTO math, and error handling. Never give it a direct DB handle, a raw-fetch tool, or a third-party API call — new capability = add the underlying route first, then a catalog entry.
- **Gmail stays read-only structurally, not just by prompt.** The catalog only reaches the read-only Gmail proxy and the local-flag routes (`email-rules`, `email-todos`); no Gmail write endpoint exists anywhere for a tool to name.
- **Deletes are prompt-gated:** the system prompt requires John's explicit in-conversation confirmation before any delete tool. Same no-fabricated-data rule as the UI — answers must come from tool results.
- **Sonnet, not Haiku or Opus, deliberately** — the five narrow uses stay on Haiku (`lib/anthropic.js` is still pinned); an agentic multi-tool assistant needs a stronger model, but John rejected Opus on cost (2026-08-09). `ASSISTANT_MODEL` in `lib/assistant.js` is the one place to change it.
- **Conversation state lives in the browser tab only** (raw Anthropic message blocks resent each turn); nothing is persisted server-side, and a successful write triggers the app-wide `refresh()` signal so every page re-fetches.
- **It can ingest images and files (added 2026-08-26)**, the same way this app's other AI imports work: `components/AssistantPanel.jsx` lets John paste, drag-and-drop, or attach a screenshot/photo, PDF, or text file (`.txt`/`.csv`/`.md`) directly into the chat. Images are downscaled/recompressed client-side via canvas when large (Vercel's serverless body-size ceiling, not a model limit, is the real constraint) and sent as Anthropic `image` blocks; PDFs go as base64 `document` blocks; text-like files are read client-side and inlined as a `text` block, since the Messages API's base64 document source is for PDFs specifically. `app/api/assistant/route.js` validates every attachment block server-side too (allowed media types, size caps) — never trust the client alone — and its history-trimming boundary check now also recognizes an array (multimodal) user turn as a safe place to start the resent window, not just a plain string one. An attachment is just conversational input, same as typed text — it never writes to the dashboard by itself; turning "here's a screenshot of X" into real data still goes through the matching tool call, same no-fabricated-data discipline as every AI import elsewhere in this app.
- **The catalog covers every domain, Mileage included (added 2026-08-26).** Mileage shipped as its own set of routes without an assistant catalog entry for a while — the "add the underlying route first, then a catalog entry" rule from the bullet above means a new route is only actually usable by the assistant once it's added to `CATALOG` in `lib/assistant.js`; it's easy to ship the route and forget the catalog half. The assistant can read full Mileage state (`get_mileage`), log odometer readings, log/delete trip-journal entries, add/update/delete scenarios (manual or leg-based), add/delete usual-trip legs and favorite places, set lease settings **and the "usual trips" baseline override** (`update_mileage_settings`'s `usual_miles`/`usual_period`/`usual_active`), and accept/dismiss/manually-add Travel Day Exclusions — so "build my baseline mileage" is doable through the assistant, not just the UI. Same discipline as everywhere else: `usual_active`, a scenario's `active` flag, and a trip's exclusion decision are never changed without John asking for that outcome.
- **A cut-off response is never silently treated as "done" (fixed 2026-08-27, a real incident).** A multi-part request (several tool calls plus a closing summary) hit the then-4096 output-token cap mid-turn; the loop's generic terminal branch fired on `stop_reason !== 'tool_use'` regardless of _why_ the turn ended, so a `max_tokens` cutoff looked identical to a normal finish and returned whatever partial (often empty) text existed — chat showed a bare "(no reply)" with no sign anything had gone wrong, and any tool call still being written when the cutoff hit was silently dropped. `runAssistant()` now checks `stop_reason === 'max_tokens'` explicitly and returns an honest message instead — naming how many changes from _earlier_ iterations this turn did go through (`actions` already reflects those) and telling John to ask it to continue rather than pretending nothing happened. `MAX_TOKENS` also raised 4096 → 8192 so a normal multi-step turn has more headroom before ever hitting this path.

**The catalog is also exposed to claude.ai over MCP (`/api/mcp/app`, added 2026-09-17, John's own request after the Health MCP connector worked).** `TOOLS` and `executeTool` are exported from `lib/assistant.js` specifically for this — `app/api/mcp/app/route.js` imports them unchanged rather than defining a second, looser catalog, so a claude.ai connection through MCP can do exactly what the in-app Assistant chat can do, no more (CLAUDE.md §7.5).

**Health is folded into `TOOLS`/`executeTool` too (added 2026-09-17, same day, once John pointed out the in-app Assistant had zero Health capability at all).** `HEALTH_TOOLS` (`get_day`, `log_food`, `log_weight`, `update_intake_entry`, `delete_intake_entry` — `lib/health-mcp-tools.js`, shared verbatim with both MCP servers) are merged into `TOOLS`, and `executeTool` dispatches a Health tool name straight to `callHealthTool` instead of a same-origin fetch — the one deliberate exception to "every tool calls this app's own api route," called out in `lib/assistant.js`'s header comment so it doesn't read as a violation of CLAUDE.md §7.5. The upshot: the in-app Assistant chat, the Health-only MCP server, and the app-wide MCP server all have identical Health capability from one implementation, never three copies that could drift. `update_intake_entry`/`delete_intake_entry` mirror `app/api/health/intake/[id]`'s own PATCH/DELETE exactly, including the re-tier-a-hand-edited-label rule — added the same session the `/health/diet` page itself gained an edit button, closing the same gap in all three surfaces at once rather than just the UI.

- **The house rules are duplicated on purpose, not copy-pasted by accident.** `systemPrompt()`'s bullet list (Gmail read-only, Idea-vs-Schedules due-date boundary, Mileage/Travel-Day-Exclusion opt-in flags, no fabricated metrics, destructive-confirm) only reaches the model inside `runAssistant()`'s own Anthropic call — an external MCP client's own model never sees it. `houseRules()` extracts that bullet list so `/api/mcp/app` can fold it into its MCP `initialize` response's `instructions` field, the closest MCP-native equivalent of a system prompt. If the house rules ever change, edit `houseRules()` once; both `systemPrompt()` and the MCP server pick it up. Per-tool "Destructive — confirm with John first" wording in `CATALOG`'s own descriptions still applies to both callers regardless, since tool descriptions are always part of `tools/list`.
- **Transport, the bearer-token gate (`APP_MCP_TOKEN`), and the OAuth wrapper for claude.ai's connector are shared with Health's MCP server**, not reimplemented — `lib/mcp-server.js` (transport + route-handler factories) and `lib/mcp-oauth.js` (the OAuth handshake itself) are used by both `/api/mcp/app` and `/api/mcp/health`. See the `health` skill for why the OAuth wrapper exists and what it does and doesn't change (short version: the token this hands back at the end of the handshake IS that server's own bearer secret — no second credential).
