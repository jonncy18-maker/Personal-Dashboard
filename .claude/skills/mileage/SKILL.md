## Mileage

**Mileage is the 7th domain — no AI, ground-truth odometer readings, and scenarios John explicitly opts into.** Built 2026-08-26 (migration 017), scoped the same day per the ROADMAP entry. `lib/mileage.js` is a pure, DB-free module (mirrors `lib/pto.js`'s shape) shared by `/api/mileage*` and `app/mileage/page.jsx`, so the pace/checkpoint math is never duplicated. Three rules that keep it honest:

- **The odometer log is the only source of cumulative miles.** `mileage_readings` (dated, one per day, upserted) is what pace and every forecast are computed from. `mileage_trips` (the point-to-point journal, geocoded via `lib/geocode.js` — the Google Geocoding API since 2026-08-26 — and routed via the free keyless OSRM demo server in `lib/route-distance.js`, no paid tile provider — routing is still free/keyless, geocoding is the one piece that moved) is a supplementary log for context; it is **never** summed into the odometer total, since two readings can legitimately disagree with what got logged as trips in between.
- **Scenarios are opt-in, never auto-applied.** `mileage_scenarios` rows carry a mileage impact per checkpoint (1/2/3-yr) and an `active` flag John toggles per scenario; a checkpoint's projection is the straight-line pace baseline plus only the **checked** scenarios' impact. Unchecked scenarios stay saved but excluded — never silently blended into what looks like the plain forecast.
- **An unconfigured lease shows an honest setup state, not fabricated defaults.** `mileage_settings`'s lease fields are nullable; `lib/mileage.js`'s `isConfigured()` gates every computation, and the page/Home card show "set up your lease" / "log a reading" rather than pretending a zero pace or empty forecast is real. No milestone-based progress or invented cost appears without real lease data behind it.

**"Usual trips" (migration 018) is a baseline override, not a second forecast.** John can state a routine rate ("300 mi/week") in a day/week/month dropdown; a single `usual_active` checkbox decides which baseline every checkpoint uses — checked, the routine rate (converted to mi/day) replaces the logged-pace baseline; unchecked, it's the logged pace as before. Either way, active scenarios add on top the same way — the toggle only swaps the baseline, never the scenario layer. The logged pace stays visible on the page even when it isn't the baseline in use, so switching the toggle is never a data-hiding operation. **The override only ever replaces the forward-looking rate, never the miles already on the odometer** (fixed 2026-08-27 — a real bug found via John's question: `usual_active`'s checkpoints were recomputing from `starting_odometer` at lease start using the hypothetical rate, ignoring the actual logged odometer entirely). Every checkpoint in both modes is now a straight line forward from the latest real logged reading (or the starting odometer if none logged yet) — `lib/mileage.js`'s `projectCheckpoint()` takes an `anchorDate`/`anchorOdometer` pair instead of always anchoring at lease start, so logging a new reading always corrects the forecast regardless of which baseline is active.

**"Usual trips" also has a detail popup (migration 019) for building the rate from real named routes instead of guessing one number.** `mileage_usual_legs` (Home → Gym, Home → Work, …, each with a `times_per_week`) is looked up the same geocode + OSRM way as the trip journal (geocoding via Google since 2026-08-26, routing still free/keyless OSRM — no Google Directions/Distance Matrix). The popup's live total (`lib/mileage.js`'s `usualLegsWeeklyTotal`) is only ever _applied_ to `usual_miles`/`usual_period` by an explicit "Use this total" click — legs are a breakdown that feeds the single baseline number, never a second one computed in parallel.

**Favorite places (migration 020) fix "Home" and "Gym" not being real geocodable places.** Labels like "Home" aren't addresses a geocoder can resolve, so every "Home"-anchored lookup silently fell back to manual mile entry. `mileage_places` pairs a label with a real address, geocoded and cached once at save time; `lib/route-distance.js`'s `fetchDrivingDistanceMiles` now takes an optional `placesByLabel` map and checks it before geocoding a bare label, so trips and usual-trip legs typed with a matching label (case-insensitive) resolve against the saved place's cached coordinates automatically. A `<datalist>` on the origin/destination fields suggests saved labels without forcing free text.

**The "Favorite places" address field autocompletes and validates against the geocoder, no schema change.** Typing ≥3 characters debounces (350ms) a call to `/api/mileage/geocode-suggest` (a thin, uncached proxy around `lib/geocode.js`'s `searchPlaces()`, since a browser can't call a third-party geocoding API directly — CLAUDE.md §2), showing a pick-list of real matches instead of a free-text field a user has to guess is correctly formatted. Picking a suggestion carries its lat/lng straight into the save payload (`POST /api/mileage/places` now accepts optional `lat`/`lng` and trusts them instead of re-geocoding), so a chosen address can't drift to a different geocode result than what was shown; a hand-typed address with no pick still saves and geocodes server-side exactly as before, unchanged. If even the Google Geocoding API has no match for a real address, a manual "Enter coordinates" fallback (added 2026-08-26) lets John paste in coordinates looked up elsewhere.

**Scenarios can be built from a usual-trip leg's frequency change (migration 021), not just a typed mile guess.** "What if the cafe trip became 3x/week instead of 2x?" — pick a saved leg and a new times/week, and `lib/mileage.js`'s `legFrequencyScenarioImpacts` computes `impact_1yr/2yr/3yr` server-side (never trusted from the client), extrapolating the extra weekly mileage linearly from lease start to each checkpoint — the same model the pace baseline itself uses. `projectCheckpoint()` is unchanged: a leg-based scenario is still just a row with `impact_1yr/2yr/3yr`, computed differently but read identically.

**Travel Day Exclusions (migration 022) are a distinct section from Forecast Scenarios — a real one-time fact, not a hypothetical recurring routine change.** John's framing: "when trips happen, normal daily drives do not happen," so a real Travel trip's days shouldn't just add to the forecast unmodeled — they should subtract the baseline driving that didn't happen. Reviewed the same way Travel's own Gmail trip-suggestion queue works: a real (non-wishlist), dated trip with no exclusion row yet surfaces in a popup — **auto-shown once per page load** if anything is undecided, or manually via the panel's "Scan travel" button (which also re-surfaces previously **dismissed** trips — dismiss is a snooze, not a permanent skip). Two outcomes: **Accept** snapshots `(current baseline daily rate) × (trip's day count)` as `miles_excluded`, computed from whichever baseline is currently active (logged pace, or the usual-trips rate if `usual_active`) — a snapshot, so it never silently drifts if the pace changes later, same discipline as a leg-based scenario's impact. **Dismiss** just records the decision so it stops auto-popping. A **manual entry** (label + date range) covers a trip Travel doesn't track (a day trip, work travel) and is always saved as accepted immediately. Unlike a scenario's linear time-scaled impact (a recurring habit change grows with elapsed time), an exclusion is a flat one-time subtraction applied in full to every checkpoint whose date is on or after the trip's end date — `lib/mileage.js`'s `projectCheckpoint()` takes an `exclusions` array for exactly this. **Whole days are excluded, not just weekends** — while traveling, the entire daily baseline pauses, not just its weekend portion.
